# Actual M9 companion constructor and sparse initialization

The passive CPU checkpoint `normal-faa-companion-constructor.json` executes the real vendor allocator under public registry inputs `System.MmFlags=101b8`, `100f8`, and `101f8`. The existing fixture attaches the captured BAR0 through a controlled caller; it does not claim full adapter startup or GPU work. `m9_faa_companion_constructor.py` regenerates the checkpoint, and `check-faa-companion-constructor.py` verifies the image, instruction pins, inputs, ownership, chronological initialization, and known-byte boundary.

For the genuine normal `101b8` input with 1 GiB VRAM, the descriptor builder at VA `cfb40` produces primary `401000/100000`, companion `501000/400000`, CPU root `901000/40000`, auxiliary `941000/40000`, and tail `981000/100000`. The selected manager child pointers are `+1c+4*selector24`, `+38+4*selector40`, `+54+4*selector5c`, `+70+4*selector78`, and `+8c+4*selector94`. Each child holds extent at `+14`, CPU aperture address at `+1c`, and GPU base at `+20`. The companion is an extension immediately following the primary partitions, selected independently for publication.

Both bit-6 controls, `100f8` and `101f8`, return real format admission and allocator success. Their actual primary extent is `104000`, companion `410000` at `505000`, CPU root `915000`, auxiliary `955000`, and tail `995000`. These values are not the shipped Linux `120000` primary extent. The Windows builder reads actual `System.AgsSize=ffffffff` at `cfc06` and the retained fixture's shared-owner `+21f050/+21f054=[0,0]` at `cfc33`; its fallback at `cfc4d` selects 16 MiB. This is a bounded CPU fixture input/branch, not evidence for installed target system RAM. The resulting additional namespace covers `40000000..40ffffff`.

The companion's initialization is sparse. The constructor calls `5bc50` with a real zero mapping descriptor and a record count of `extent/16`. Its CPU fallback store `5bcf0` writes only the first DWORD, zero, then advances the pointer by 16 at `5bcf9`. For `101b8`, exactly 262144 spans of four bytes are known, totaling 1 MiB within the 4 MiB owner. For each bit-6 control there are 266240 such spans, totaling `104000` within `410000`. Bytes 4 through 15 of every initial record remain unknown. A full-table memset would manufacture contents the real constructor does not supply. Actual per-resource allocation updates subsequently write the first three DWORDs and retain the fourth; the independent secondary-page capture covers those updates.

The actual chronological constructor order is window publication, primary clear, companion first-DWORD clear, 256 MiB CPU-root identity initialization, compact activation `31c=f,0,1`, `30c=1000`, auxiliary clear, tail clear, and terminal activation `31c=c,1`. Window publication is primary `132c/1330/1334`, companion `1320/1324/1328`, CPU `360/364`, tail `f64/f68`, and primary mirror `f74/f78/f7c`. Every base/base/limit triple uses its selected child; the limit is inclusive of the last 4 KiB page. Source `5b230..5b3b3` and the chronological passive instruction markers pin this order. No GPU submission is present during these clears.

Bit 8 has a separate demonstrated CPU service effect. At `4502f`, the actual MmFlags getter is tested for `100`. The set path creates an additional service with `a1900` and wraps it with `a1ba0`, publishing resource-owner `+48`; `101b8` and `101f8` produce a nonzero owner while `100f8` leaves it zero. Both bit-6 controls have the same observed table ranges, sparse initialization, and MMIO/activation sequence. This does not identify additional unobserved GPU effects of that service.

The full normal bit-6 queue controls remain separate from constructor admission. Both `100f8` and the previously documented `101f8` path reach genuine `458a7 -> 19d60 -> IOCTL23306c`, with eight input bytes and twelve output bytes. The original strict miniport bridge stopped at that unreviewed OS mapping request. The real handler/OS contract extension below subsequently closes the `101f8` CPU frame; no synthetic allocation or GPU reply is used. Bit 6 and bit 8 differ between `100f8` and the closed `101b8` frame, so that boundary must not be attributed solely to bit 8.

The native private candidate can use the source-derived selected-owner grammar and actual sparse stores, retaining a bounded class-1 namespace and all backing ownership. Its Linux DMA allocation contract must be proved independently. Publishing a companion while retaining old conflicting CPU/tail windows, or changing the primary extent without relocating existing class-1 slots, would mix incompatible manager layouts. This checkpoint makes no claim that adding the companion fixes the observed black output.

## Full bit-6 frame and actual scatter metadata closure

The strict real `7190e -> 7203d` MDL allocation bridge, together with the actual `247f4` one-MiB SkipBytes contract, now permits the full `101f8` CPU frame to return through triangle and resolve. The source-known capture `normal-faa-scatter-metadata-101f8.json` retains 33 genuine `23306c` replies, 34 live OS MDLs, 1841 actual guest writes to their mapped backings, and exactly 7348 known backing bytes. The new passive `m9_mdl_inputs.Observer` joins each write segment to its actual retained MDL PFN and exports no untouched allocation bytes. A separate guest cross-page write check verified that it exports only the four produced bytes and joins both page segments correctly.

The companion scatter metadata is **not** the local direct-mapping zero grammar. The 34 actual scatter calls use CPU fallback `5ba25/5ba27/5ba2d/5ba33`. Their last three words are `[0, N, 0]`, where `N` is the mapping page count: 32 queue mappings with flags `30` and `N=64`, one counter mapping with flags `110` and `N=1`, and a later flags-`30` mapping with `N=80`. All 12 source bytes are known from actual prior guest stack writes. The first and third words were last written by `5b3fe`, the preceding compact mapper's descriptor `rep movsd`; the middle word was last written by `5b725`, its page-progress update. Those physical stack addresses alias `5b750`'s fallback locals `EBP-38/-34/-30`. The sparse constructor's initial unknown bytes do not imply these later CPU-produced metadata words remain unknown.

The observer also pins each real PFN load and packed first word. Flags `30` produce PTE low nibble `b`; flags `110` produce `a`. The source folds the upper physical-address nibble into PTE bits 11:4. The counter PFN source is a typed CPU scatter proxy, not a raw NT MDL pointer; the later 80-page mapping uses a prefix of an owned 85-page MDL. Neither distinction is converted into invented contiguous ownership. The checker verifies those bounds, all captured packed words, every metadata word's known prior writer, and every exported MDL byte against chronological actual guest writes.

This is the observed full-frame CPU path and its particular stack-derived source values. It does not establish universal scatter metadata for arbitrary future contexts or the unused active staging branch at `5b833`. The direct local allocation grammar remains three produced words `[page|8,0,0]` with a retained unknown fourth word. The native private candidate must preserve those distinct source paths and real ownership; the pending generic zero-DMA metadata helper is insufficient evidence for this full vendor flow.

The fresh frame has 33 mapped raw NT MDL prefixes, one additional live unmapped MDL, and one separate typed counter PFN proxy.
