This note fixes the exact boundary between the M9148 command evidence and the
current clean-room kernel/Mesa code.  It uses the settled single-triangle
fixture in `captures/m9x-linux-gltri-20260914`, and it does not rely on a live
target.  Reproduce the checks with:

```sh
python3 tools/m9-first-triangle-stream-evidence.py --self-test --sites
python3 tools/m9-first-triangle-resources-evidence.py --self-test
```

The result is deliberately narrower than "triangle ready."  The primary
requester and memory-writeback completion path have passed hardware.  The
two-pass command ordering and the semantic relocation classes below are exact.
A cold, relocatable triangle still lacks several resource images and derived
surface fields and must not be submitted by copying vendor values.

## Current bring-up boundary

The independent `m9x_drm.ko` has completed 256 consecutive kernel-owned
three-dword no-op fences and one further fence after the DRM loader name was
split from Parhelia.  That establishes primary requester fetch through
`400=start|2`, `404=exclusive_end`, index `e3` writeback through the address at
`106c`, and bounded polling of coherent memory.

General execution is still disabled.  `M9_SUBMIT(VALIDATE_ONLY)` patches a
private copy and discards it.  There is no scheduler job, resource reservation,
copied command execution, syncobj result, preprocessing pass, GPU clear, or
render readback in the current kernel/Mesa path.

The Mesa `m9_resource_clear_linear()` helper is a CPU row-major clear of a
mapped 16- or 32-bit linear BO.  It is useful for a sentinel background before
the first draw, but it is not evidence that the 3-D engine can clear.  The
statically recovered whole-page and rectangle-draw GPU clear paths remain
separate validation items.

## Exact saved operation

The source files are pinned as follows:

```text
bm-12.bin
  abb4ac761fd529754a6bb62ad0e8e25013967ec8c1f375ed65955991a8f0d05c
execute-12.bin
  f009dbf9ec3331e5cc73ed0172ac2356a17268009484d81b1cb2c09e84a08dfa
```

The private vendor ExecuteDma envelope selects three contiguous logical ranges:

```text
preprocess  [000,268)  38 decoded packets, H03 [0,4)
raster      [268,4bc)  37 decoded packets, H03 [0,3)
completion  [4bc,4e8)   3 decoded packets
```

Ordinary records in that private buffer have a count dword.  H03 draw triples
do not.  The new DRM UAPI does not need to reproduce these private count words.
After removing them while preserving every raw indexed packet and draw in
order, the three ranges are:

| range | raw dwords | bytes | SHA-256 |
| --- | ---: | ---: | --- |
| preprocess | 118 | `0x1d8` | `5046474507c6a4af9f8296106562a5e97f63e9ca3cf5f0960401523c93ab3419` |
| raster | 113 | `0x1c4` | `abd5152aafed2dbbe6d037014187f97edf5f33c44c43143668f619f670931322` |
| completion | 8 | `0x20` | `0757e5493def5483de9cbfde09bab17c7cbc048edc385d6d09f6dcf228077dfb` |

These hashes are a deterministic canonicalization of the captured packet
order.  They do not prove that the vendor kernel posted all 239 dwords as one
primary interval: ExecuteDma may post individual counted records.  A new
kernel may concatenate validated raw packets only after the state transitions
and intermediate target ordering below are generated by the kernel.

The producer/consumer join is exact:

```text
preprocess [b0,b4,b8,b2] = [113c1000,113ee000,11404800,113d7800]
raster     [00,01,02,03] = [113c1000,113ee000,11404800,113d7800]
```

Both passes bind the same captured external tuple:

```text
69=11e42000  6a=25010000  68=00000000
6b=00001030  6c=40c3a301
```

The raster pass additionally binds color `b0/b1=11ee9000/cc210140`, ordinary
depth `b8/b9=11f39000/fa210140`, auxiliary depth
`ba/bb=11f89000/f0010140`, and clip endpoints
`f5=c4=0,f6=c5=00f00140`.  Those numeric addresses are fixture values, not
values a new driver can replay.

## Typed relocation and BO contract

The table uses dword offsets in each count-free canonical range.  "Open"
means the address nature is certain but the narrow read/write role still needs
a resource snapshot; the first diagnostic must keep it resident with both
accesses.

| range/dword | index | semantic target | operand access | required encoding |
| --- | ---: | --- | --- | --- |
| P/15 | `b0` | transient 0 output | write | untagged, at least 256-byte aligned |
| P/18 | `b2` | transient 3 output | write | untagged, at least 256-byte aligned |
| P/21 | `b4` | transient 1 output | write | untagged, at least 256-byte aligned |
| P/24 | `b8` | transient 2 output | write | untagged, at least 256-byte aligned |
| P/57 | `00` | canonical vertex source | read | system address plus captured low tag 1 |
| P/61, R/61 | `c2` | 0x1080-byte common resource-bank backing | conservative read/write | untagged; observed page alignment |
| P/66..67 | `8d/8e` | system range `[+0x10,+0xc0)` | read | same system BO, each address plus tag 1 |
| P/105, R/103 | `69` | external fixed-fragment database | read | untagged emitted address; descriptor reports 4-KiB alignment, but translation to the logical database is unresolved |
| P/111, R/109 | `6c` | linked record at `+0x300` | read | same system BO, 0x80 alignment, tag 1 |
| R/22 | `b0` | linear color RT0 | write for this unblended draw | untagged, at least 256-byte aligned |
| R/25 | `b8` | ordinary depth | conservative read/write | untagged, at least 256-byte aligned |
| R/28 | `ba` | auxiliary depth | conservative read/write | untagged, at least 256-byte aligned |
| R/31 | `be` | auxiliary bound-surface resource, static usage 8 | conservative read/write | untagged; observed page alignment |
| R/53..58 | `00..03` | transient inputs 0..3 | read | exact output permutation above |
| R/66..67 | `8d/8e` | system range `[+0,+0x10)` | read | same system BO, each address plus tag 1 |
| F/1 | `1b` | completion writeback word | write | kernel coherent address plus tag 2 |

The four transient BO references must therefore accumulate read/write access
for the complete job even though each individual operand has one direction.
RT0 is write-only only for this captured blending-disabled path.  A general
color attachment becomes read/write when blending or another destination read
is active.  Depth and the auxiliary allocation stay conservatively read/write
for the first diagnostic because their descriptor bindings are live even
though depth test is disabled.

`8d/8e` are end-exclusive resource ranges in the same system allocation as the
linked state, but they are not 0x80-aligned linked-record selectors.  They need
their own range relocation kinds.  Reusing `RESOURCE_6C` would incorrectly
enforce 0x80 alignment.  Likewise, `SPECIAL` is too broad for `00..03`, `be`,
and `c2`; each occurrence needs a pass-specific semantic role.

Two multiplexed forms are particularly important:

* preprocessing index `00=40f52001` is an address and index
  `01=f2fe014f` is a literal descriptor;
* raster indices `00..03` are four addresses;
* preprocessing `be=3` is literal while raster `be=112c1000` is an address;
* startup state can use `c2=4` as a literal while the triangle uses a resource
  address.

A validator which assigns relocation kinds from the index byte alone cannot
accept this operation safely.  It needs a kernel-selected template/state class
or a grammar which establishes the role before checking relocations.

Indices `e3`, `e6`, `43`, and `1b` stay kernel-owned.  Sequence 12 carries the
ordered target values:

```text
e3: 270,280 | 290,2a0,2b0 | 2c1
43:             2a0       | 2c0
```

The new kernel should reserve six consecutive 0x10 target values, rewrite all
of these transition/dependency operands coherently, and expose only the final
masked target as the job fence.  The final captured footer shape is:

```text
1b = completion DMA address | 2
e6 = 3
e6 = 2
e3 = final_target | 1
43 = final_target
```

## Audit of the current builders

The production split is clean, but the current builders stop before this
operation:

* `m9_batch_emit_regs()` emits count-free raw indexed packets, while the
  documentation still says `m9_batch.[ch]` owns counted records.  Count-free
  is a sensible canonical UAPI, but the UAPI and validator documentation must
  choose it explicitly.
* No builder emits the preprocessing source, its four outputs, the exact
  transient permutation, the `8d/8e` ranges, the `be/c2` resources, or the
  kernel-owned transition sequence.
* `m9_batch_bind_program()` preserves write order but merges captured packet
  groups.  The first diagnostic should preserve the captured grouping until a
  differential proves merging harmless.
* `m9_batch_emit_triangle_raster()` emits only ten state values.  It omits
  mandatory captured groups including `f0/ef/d7`, `88..8a`, `23`, surfaces,
  resource ranges, and internal resources.  Its `a8` expression also has no
  comparison-function input and does not reproduce captured `0038038a` from
  its default booleans.
* `m9_batch_bind_surface()` marks every surface only WRITE.  It cannot express
  depth read without update or destination reads for blending.
* Kernel `m9_index_reloc_kind()` blanket-marks `00..03` as `SPECIAL`, misses
  address-bearing `8d/8e`, raster `be`, and `c2`, and consequently both demands
  a relocation for literal preprocessing index `01` and accepts raw addresses
  in other slots.
* The validator rejects `af`, which appears in the captured preprocessing
  range, and rejects kernel-owned `e3/e6/43` without providing a kernel
  constructor to replace them.

These are implementation gaps, not evidence gaps in the two-pass ordering.
They explain why the present stack can validate small synthetic batches but
cannot submit the saved triangle.

## Missing bytes before a safe triangle

The saved command stream alone is insufficient for a from-scratch replay:

1. The canonical vertex source at captured `40f52000|1` was not snapshotted by
   the M9148 wrapper, but its exact bounded producer is closed.  M9148 emits
   the same `0x14` span and float2-position/RGB-float declaration as two
   hash-pinned M0528 CPU-ring captures that expose `{x,y,r,g,b}`.  The default
   green triangle has three exact records; duplicating record 2 into the
   alignment/prefetch record gives a fully initialized 80-byte image with
   SHA-256 `58bd76a39629399e0da5241acea797223c6b68c8eaf83dec7161a6e095845f3a`.
2. The four transient allocation contents were not captured between passes.
   Their address routing is exact and four bases repeat with three exact
   `0x16800` differences.  Four independent `0x16800` writable diagnostic BOs
   followed by guards conservatively reproduce that lattice, but the value is
   not proved as the hardware minimum or logical stream extent.
3. The bytes covering the baseline linked record at system offset `0x300` are
   saved in the later GLSL A fixture, including
   `m9x-linux-glsl-ab-20260914/fs/resource-15.bin`.  An aligned-dword scan of
   both adjacent 0x580-byte A/B slots across sequences 15, 19, and 23 finds no
   pointer into the captured local aperture or system allocation.  Their
   embedded GPU-BO relocation map is empty.  This is not a cold-replay permit:
   the fixed-function slot selected at offset `0x1600` embeds nine 64-bit
   `0x2b94...` process addresses.  Raw fixed-slot replay is therefore rejected;
   a new context needs a newly serialized record or a validated inline-chain
   replacement.
4. `c2` and raster `be` are definite resource addresses.  C2 is tied to a
   captured 0x1080-byte allocation and paired usages `0x13/0x14`; the two
   submits between allocation and draw are fence-only, so there is no GPU
   initializer.  Zeroing it and retaining it read/write for the whole job is a
   deterministic guarded probe, not proof of the missing initial bytes.  BE is
   tied to the bound-surface auxiliary pair with usage 8.  An
   M0528 aperture trace proves at least `0x3f00` zero bytes following the same
   BE base encoding, but exact M9148 extent and bytes remain open.
5. Raster `ab/ac` are ordinary packed surface state, not addresses.  Windows
   static code supplies the exact descriptor-to-halfword formula.  It also
   leaves inactive local halfwords uninitialized, explaining why all twenty
   single-RT topology captures have slot 0 equal to `ffff` while the upper 48
   bits vary.  Initialize inactive slots to `ffff`; the bounded one-RT value is
   deterministically `ab=ac=ffffffff`.  Arbitrary MRT requires its active
   per-surface table entries.
6. A fresh context requires the invariant 80-slot `8f/90..9f` image captured in
   setup sequence 0.  Its `0x280` payload, selector/port grammar, and equality
   across setup sequences 0, 8, 10, and 14 are pinned.  Its smallest safe cold
   surrounding envelope has not been hardware isolated, so the first
   diagnostic should retain the full sequence-0 setup envelope.

These items leave two resource gates for an exact cold low-level triangle:
M9148 BE allocation/initialization beyond the cross-family guarded lower bound,
and construction of a fresh linked record or validation of the inline fixed
chain.  The bounded canonical source bytes, one-RT AB/AC policy, and guarded
C2 zeroing policy are now specified; exact C2 bytes remain conditional on that
probe succeeding.

## Safest first hardware sequence

Do not make the first executable UAPI a general command submission.  Add a
second literal opt-in diagnostic which accepts no user command bytes and builds
one kernel-owned known-layout job.

1. Keep the module in a target temporary directory and load it only with the
   existing `m9_enable=1` and diagnostic gate.  Keep KMS and IRQ changes out of
   this render-only test.
2. Re-run one no-op fence after load.  Stop if the writeback, MMIO readback, or
   PCI bus-master state differs from the proved result.
3. Allocate every operand as a distinct DMA32 BO with page guard/sentinel
   regions.  Keep command, source, system record, `69`, `c2`, `be`, four
   transients, RT0, depth, auxiliary depth, and fence storage separately
   identifiable.  Give each transient at least `0x16800` writable bytes and a
   following guard as a conservative probe; do not expose that observed spacing
   as a hardware extent.
4. CPU-clear the linear RT to opaque magenta and fill all guards and unused
   resources with distinct sentinels.  Publish CPU writes before the GPU job.
5. Before enabling execution, pass the complete templated operation through
   validate-only with every address zeroed and every operand represented by the
   typed relocations above.  Run negative cases for a missing relocation,
   literal/relocation confusion at `01` and `be`, overlap, bad tag, bad range,
   and end overflow.
6. Close the remaining byte/layout items above.  Then upload the pinned
   invariant context state and execute exactly one preprocess plus one raster
   pass with six kernel-owned transition targets and the expanded footer.
7. Use one absolute 100 ms deadline.  On timeout, record both fence words,
   `314/31c/400/404/448`, `1068/106c`, `8f0`, all IRQ banks, and every BO hash;
   issue at most the already proved single progress kick and wedge rendering if
   completion still fails.  Leave all possibly reachable DMA storage allocated
   until bus mastering is disabled.

A successful first result requires all of the following:

* final writeback masked by `~0xf` equals the final reserved target;
* the four transient payloads change and their guards do not;
* RT0 retains magenta at the corners and has RGB `00ff00` at several points
  strictly inside the captured triangle, with alpha ignored for comparison;
* only the expected triangle bounding region changes from the sentinel;
* depth and auxiliary guards remain intact, and every input/system/program BO
  declared read-only is byte-identical;
* a second no-op fence completes, then module unload disables bus mastering.

Only after this kernel-owned diagnostic passes should the same template be
opened to Mesa with typed BO handles and a returned syncobj point.  General
state packets, shaders, and arbitrary draw streams remain later gates.
