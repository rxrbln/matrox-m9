# Allocation-dependent FAA companion page clear

The normal frame contains one inline whole-allocation clear whose GPU allocation page indices are encoded inside payload words, outside the `25680` relocation callback. The captured primary's `11d8..1220` words cannot remain immutable when the companion allocation moves. Their producer is the actual fast-clear path `b5e70`; `b5eae` reads resource `+198` as the GPU allocation address, and `b5ff5` reads resource `+1bc` as its logical clear extent.

The actual companion extent is 618496 bytes (`97000`, 151 pages), within the separately rounded `98000` backing allocation. The spare 152nd allocation page has no source clear operation. Both genuine profiles start their companion at page remainder one (`1021000` and `1039000`), producing seven leading pages and eighteen full eight-page groups, nineteen payload words. Native allocation `2f0e000` starts at remainder six; its same 151 pages require two leading pages, eighteen full groups, then five trailing pages, twenty words. Keeping the old nineteen masks would clear the wrong pages.

The exact arithmetic is source closed. For `base_page=resource+198 >> 12` and `pages=ceil(resource+1bc/4096)`, `b6001..b6026` splits an initial partial group from the remaining pages. `b60b5..b60c1` forms `((base_page & ffff8) | d00000) << 5`. The low byte is the selected-page mask. `b6101` writes a partial head; `b6143` writes each full group and advances bits `1ffff00` by `100`; `b61ae` writes a partial tail. The counted packet header is `45e62b2a/454545e6/ffff/(20000000 | (payload_words-1))`.

The selected padding mode is separately retained by passive full-frame proof `e1557033`: genuine `b5f86` reads owner `28000000+1c` as zero, and `b6028` observes its saved bit-0 flag as zero. This is the selected device state in the controlled joined fixture, not a separately queried physical-adapter capability. Thus the bounded replay takes the actual no-padding path; it does not invent optional `0/1` tail words.

`tools/m9-faa-clear-page-runs.py` executes the real `b5ff5..b61b3` x86 instructions in Unicorn with explicit bounded CPU inputs, stopping before the command-stream virtual call. `normal-faa-clear-page-runs.json` retains image hash, instruction pins, exact outputs for both captured allocations and all eight native base alignments. Every selected page is decoded independently and equals exactly the 151 requested pages. This isolated arithmetic fixture supplies no allocation, GPU reply, completion, or whole-frame assertion.

The kernel's private rebuild validates the original clear headers, count, footer and all nineteen original words before mutation. It patches the existing 53 address and 26 tracker fields at their original source offsets, then moves the already patched suffix once, emits the new page masks/count, and submits the adjusted primary prefix length. For `2f0e000` the first mask word is `1a05e1c0`, the last is `1a05f41f`, and the primary grows from 5676 to 5680 bytes. The exact secondary batches and their owner-relative endpoint offsets remain unchanged. No opaque FAA allocation is CPU cleared.

The kernel fixture `m9x/tests/faa-clear-cpu.py` extracts and compiles the actual native encoder/rebuilder helpers. It applies the real fixed address/tracker tables first, compares every emitted word with the vendor-instruction artifact, verifies exact prefix/suffix/secondary byte preservation, and rejects damaged original words/count, undersized owners/capacity, and overflowing ranges before mutation. The actual kernel object also compiles. These close the CPU packet-generation change; a successful hardware image remains a separate requirement.
