# Fresh prepared startup and the c0 prefix

The source-only prepared fixture `5378c764` executes the genuine conversion
constructor and preparation before queue creation. The original first
`4e2fc` common+20 load remains unexecuted. Its independent source flush emits
4980 primary bytes and targets c0. No earlier hardware receipt is an input.

`check-faa-prepared-prefix.py` validates both complete source manifests and the
fresh constructor/preparation helper proof. It compares 28 consumed backing
owners, their domains, allocation sizes, mapped prefixes, view formats and
shapes, four typed addresses and fourteen timeline fields. Both companion
and primary page clears are regenerated with the shipping `b5e70` arithmetic
at host comparison coordinates. All known images then match; all seven LOCAL
input spans already match byte for byte without normalization. The two
original clear segment locations, lengths and owner roles match. The fresh
fixture's allocation placement therefore changes neither these consumed
inputs nor the c0 command semantics.

This does **not** prove identical whole startup. Actual preparation calls
`5b3c0` then `5b750` with the same eleven-word local descriptor, a 128-page
extent and flags zero. It adds an independent 0x80000-byte d0 backing owner.
The extra six source `59b82` MMIO stores are the existing compact/secondary
publisher before queue creation. Deleting that publisher leaves all 612
previous MMIO rows, including read values, identical and ordered. Repeated
identical publisher groups allow bytewise insertion positions 56 and 62;
this comparison does not invent a unique timestamp from their values.
Constructor timing independently establishes the before-queue admission.
Requester and common-counter/restore descriptor GPU values remain identical;
each source checker verifies the distinct CPU object identities and the
primary cursor translation expression.

The fresh native plan appends local owner28 without changing the consumed
owner indices. It derives its size from that actual descriptor, retains
unknown backing bytes, and exports no known span for it. Native admission
must allocate and publish this live owner through the existing local mapper
before the ordinary owner loop and first primary submit. The generated
`M9_FAA_STARTUP_LOCAL_OWNER` and `M9_FAA_STARTUP_LOCAL_BYTES` express that
requirement; they are not captured runtime addresses. This proof does not
assert a value for the optional companion record's unwritten fourth DWORD.

Two original 0x201000-byte contiguous OS RAM allocations also remain retained
in the fresh source. They have unknown contents and no current GPU operand
or mapped GPU consumer. The first native prefix omits these CPU-only owners;
a later consumer must establish their complete live ownership and address
domain before use. Neither preparation readiness nor matching c0 inputs
permits using old receipts or attaching these new wrappers to an old graph.

The retained-store checker derives the exact separate 29-owner plan from all
four frozen source artifacts. It requires the owner28 startup publication log
before initial counters and primary submission and requires both bounded
owner28 observations. Its CPU test doubles are validator tests, never GPU
receipts. Hardware qualification and any subsequent caller continuation
remain separate requirements.
